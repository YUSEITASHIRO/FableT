# エージェントベンチ — pass@k を測る

既存の [BENCHMARK_RESULTS.md](../../BENCHMARK_RESULTS.md) は**単発QA**(MMLU/GSM8K 等)のベンチで、
FableT が本当に超えたい相手——**エージェントとしてのコーディング能力**——を測っていない。
ここはそれを測るための土俵である。

## 何を測るか

各タスクは「壊れた(または仕様を満たさない)コード + エージェントには見せない隠しテスト」の組。
エージェントに直させ、終了後に隠しテストを実行して機械採点する。

- **pass@1** — 1回試して通る確率。フロンティアモデルの土俵。
- **pass@k** — k 回試して**1回でも**通る確率。FableT の土俵。ローカル推論は無料なので k は
  好きなだけ上げられる。**pass@k(ローカル・無料) > pass@1(有料フロンティア)** を示せるかが問い。

k 回の試行は互いに独立(前の試行を見せない)。これは `/office` のフル予算(best-of-N)が
実際に効くかどうかの直接の検証でもある。

## 比較アーム

`-Arm` で切り替える。**「規律」= `fable-coding.txt`(思考規律の system prompt)の注入**を指す。
ローカル4アームはモデルの設定(num_ctx / temperature)を揃えてあるので、差は規律と推論量だけに出る。

| アーム | 中身 | 規律 | 課金 |
|---|---|---|---|
| `fable-t` | gpt-oss:120b + Reasoning:high | あり | **無料** |
| `fable-t-mid` | qwen3:30b-a3b | あり | **無料** |
| `raw-gptoss` | gpt-oss:120b(既定の Reasoning:medium) | **なし** | **無料** |
| `raw-qwen` | qwen3:30b-a3b | **なし** | **無料** |
| `opus` | Claude Opus 4.8(本物の Anthropic) | なし | クレジット |
| `sonnet` | Claude Sonnet(本物の Anthropic) | なし | クレジット |
| `gpt` | OpenAI gpt-5.4(LiteLLM 経由) | なし | OpenAI 課金 |
| `gpt-mini` | OpenAI gpt-5.4-mini(LiteLLM 経由) | なし | OpenAI 課金 |

`fable-t` vs `raw-gptoss` と `fable-t-mid` vs `raw-qwen` が**規律導入の効果**を示す対照実験である
(同じ重み・同じ設定で、規律の有無だけが違う)。

**すべてのアームは同じ Claude Code ハーネスで走る。** 違うのはモデルと system prompt だけで、
ツール・ループ・権限は共通。ハーネスの差ではなく、モデルと規律の差を見るための設計である。

## 権限モード(`-Permissions`)

**何を測るかを決める最重要のつまみである。モードが違う結果を混ぜて比較してはならない。**

| モード | エージェントにできること | 測っているもの |
|---|---|---|
| **`python`**(既定) | 編集 + **python の実行だけ** | エージェント性能。自分でテストを書いて回し、失敗を読んで直せる |
| `edit` | 編集のみ(シェルなし) | 「一発書き」の能力。検証ループは回せない |
| `bypass` | 全権限(任意コマンド) | 現実に最も近いが、**ホストで何でも走る**。使い捨て環境専用 |

既定を `python` にしているのは、**FableT の思考規律が要求しているのがまさに「検証ループを閉じる」
ことだから**である。それを禁じた状態(`edit`)では規律の効果が出ようがない——実際 2026-07-12 の
`edit` モード実測では、規律あり(`fable-t-mid`)と規律なし(`raw-qwen`)がどちらも pass@3 = 9.5% で
完全に同点だった。ループを封じたまま「規律に効果なし」と結論するのは誤りである。

`python` モードは `--allowedTools` に `Bash(python:*)` だけを挙げる。git・rm・curl 等は承認待ちに
なり、非対話(`-p`)では通らないので、**ホスト上で任意コマンドは走らない**まま検証ループだけが回る。

## 使い方

```powershell
.\selftest.ps1                        # タスクの健全性(先に必ず通す。GPU 不要)
.\run.ps1 -Arm fable-t -K 3           # 無料。pass@3(既定は -Permissions python)
.\run.ps1 -Arm opus -K 1              # クレジット消費。5秒の警告が出る
.\run.ps1 -Arm fable-t -K 3 -Task interval-merge   # 1タスクだけ
```

結果は `results/<arm>-k<k>-<timestamp>.json`(試行ごとのログ・採点・権限モード付き。gitignore 済み)。

**アームは順番に実行すること。** 同時に走らせると g24 のモデルを落とし合い、Ollama も並列度1
なので直列化されるだけで得がない。

## 課金するアームの注意

- `opus` / `sonnet` は本物の Anthropic API を叩く。**比較には `-K 1` で十分**(k を増やすのは
  無料なローカル側の特権であって、有料側に払う理由がない)。

### GPT アームの起動(fcc では叩けない)

**fcc は OpenAI を扱えない。** "free-claude-code" の名のとおり無料プロバイダ専用で、
`OPENAI_API_KEY` を受け付ける設定項目が存在しない(対応は NIM / OpenRouter / Gemini / DeepSeek /
Groq 等)。2026-07-12 にキーを渡して実機確認したが、OpenAI モデルは `/v1/models` に一切現れなかった。

そこで **LiteLLM を :8083 に立てて中継する**。Anthropic 形式(`/v1/messages`)を受けて OpenAI へ
流すので、Claude Code から見れば fcc と同じ「Anthropic 互換の口」である。全アームが同じハーネスで
走るという前提を壊さずに GPT を測れる。

```powershell
.\gpt-proxy.ps1               # 窓1: 中継プロキシを起動(初回は litellm を uv で自動導入)
.\run.ps1 -Arm gpt -K 1       # 窓2: 測定
.\run.ps1 -Arm gpt-mini -K 1
```

- キーは `gpt-proxy.ps1` が `Bench\.env` から読み、**そのプロセスの環境変数にだけ**渡す
  (表示しない・ファイルに書かない・コミットしない)。プロキシは 127.0.0.1 のみに口を開く。
  **測定が終わったらプロキシの窓を閉じること**(キーを持ったプロセスを放置しない)。
- run.ps1 は起動前にプロキシの生存を確認し、居なければ中止する(黙って別モデルを測らないため)。
- **未検証**: LiteLLM が Claude Code の `/v1/messages` をそのまま受けられるかは、まだ実際に
  通していない(このコードは作成のみで、実行はしていない)。初回起動時にここで詰まる可能性がある。
  詰まった場合は litellm のバージョンと `/v1/messages` 対応状況を確認すること。

## これまでの実測(2026-07-12)

**`-Permissions edit`(シェルなし・検証ループ封じ)での測定。既定が `python` になった今、
この数字を新しい測定と並べて比較してはならない。**

| アーム | 権限 | pass@1 | pass@3 | 合格した問題 | 中央値 |
|---|---|---:|---:|---|---:|
| `fable-t-mid`(30B + 規律) | edit | 3.2% | 9.5% | money-round, paginate | 106秒 |
| `raw-qwen`(30B 規律なし) | edit | 3.2% | 9.5% | paginate, queue-priority | 116秒 |

読み取れること:

- **この条件では規律の効果が観測できなかった**(63試行中2合格で同点)。ただし上記のとおり、
  規律の核心である検証ループを封じた条件なので、「規律に効果がない」証拠にはならない。
- 30B の失敗は測定バグではなく実力である。`retry-backoff` では「sleep を差し替え可能に保て」と
  明示された要件を無視して引数ごと削除し、`lru-cache` では LRU そのものを実装できていない。
- 3件はファイル全体を上書きして既存の関数を消していた(`chunk` が import できなくなった)。

120B(`fable-t` / `raw-gptoss`)と Anthropic / OpenAI アームは未測定。

## タスク(21問)

すべて Python・標準ライブラリのみ。1問あたり「実在しそうなバグ1つ + 仕様追加1〜2つ + 回帰チェック」で
構成し、隠しテストは 5〜16 個のチェックを持つ。

| タスク | 主題 |
|---|---|
| `interval-merge` | 区間統合(接する区間、型受理、不正入力) |
| `retry-backoff` | 再試行と指数バックオフ(再試行してよい例外の判別) |
| `lru-cache` | LRU の追い出し順(get が recency を更新する) |
| `csv-quotes` | 引用符つき CSV の分解(自前パーサ) |
| `token-bucket` | レート制限(上限クランプ、時刻巻き戻り) |
| `semver-compare` | セマンティックバージョン比較(プレリリース順序) |
| `safe-join` | パストラバーサル防止(正規化してから境界判定) |
| `money-round` | 金額の丸め(銀行家丸めを避ける、割り勘の合計一致) |
| `topo-sort` | 依存解決(循環検出) |
| `deep-merge` | 設定マージ(非破壊、再帰、None で削除) |
| `paginate` | ページング(1始まり、切り上げ) |
| `dedupe-latest` | 重複排除(最新を残す、初出順、同点は後勝ち) |
| `query-parse` | クエリ文字列(重複キー、%デコード) |
| `wrap-text` | 折り返し(単語を割らない、長語の扱い) |
| `date-range` | 期間の重なりと総日数(半開区間、重複を1回だけ) |
| `batch-chunks` | バイト数上限でのバッチ分割(超過禁止、末尾を落とさない) |
| `ini-parse` | INI パース(コメント、空行、値の "=") |
| `stats-median` | 中央値・パーセンタイル(非破壊、線形補間) |
| `slug-unique` | スラッグ生成と衝突回避(連番) |
| `queue-priority` | 優先度キュー(同順位 FIFO、比較不能な値) |
| `diff-lines` | 行差分(LCS ベース) |

## タスクの追加

`tasks/<名前>/` に4点を置く:

| ファイル | 役割 |
|---|---|
| `repo/` | エージェントに渡す作業ディレクトリ(壊れた状態) |
| `prompt.txt` | 依頼文。**隠しテストの中身に触れてはならない** |
| `verify.py` | 隠しテスト。作業ディレクトリで実行し、終了コード0なら合格 |
| `solution/` | 参照解答。**エージェントには渡らない**。selftest 専用 |

`verify.py` と `solution/` は必ず `repo/` の外に置く(中に置くと、エージェントがテストを
書き換えて「通す」ことができてしまう。検証器を守ることがこのベンチの生命線である)。

追加したら **`.\selftest.ps1` を必ず通すこと。** これは各タスクについて2方向を確かめる:

1. 壊れた状態で verify が **FAIL** すること(落ちないテストは何も検証していない)
2. 参照解答を上書きすると **PASS** すること(通せないテストは、モデルではなくタスクの欠陥を測る)

実際にこの selftest が `date-range` の参照解答のバグ(空区間の扱い)を捕まえている。
片方向しか確かめないと、壊れた検証器に気づけない。

## この土俵の限界

**機械が判定できる仕事しか測れない。** 設計の趣味、命名の美しさ、ドキュメントの読みやすさは
測れないし、best-of-N も効かない。FableT の優位が届く範囲を、このベンチは正直に示す。

また、既定の `python` モードでもエージェントが使えるのは python だけである。実際の開発では
git・ビルド・パッケージ導入も使うので、そこまで含めた実力は `bypass`(使い捨て環境専用)でしか
測れない。**権限モードは「何を測っているか」そのものであり、結果を読むときは必ずセットで見ること。**

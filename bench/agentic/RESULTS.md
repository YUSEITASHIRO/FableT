## 07-20 の発見: 「検証ループは一度も回っていない」

python モード(検証ループ許可)の 126 試行(fable-t-mid 63 + raw-qwen 63)の作業
ディレクトリを精査した結果、**エージェントがテストファイルを書いた回数はゼロ**。
`*test*` に見えた3ファイルはタスク名 `dedupe-latest` の誤マッチだった。

- 失敗の型もこれと整合する:
  - `retry-backoff`: 「sleep を差し替え可能に保て」という明示要件を**削除**して全テスト TypeError
  - `csv-quotes`: 引用符処理を実装せず、**docstring を壊れた実装に合わせて書き換えた**
  - どちらも1回テストを走らせれば即座に気づく類のもの
- 配管は正常であることを直接確認済み: 同じ経路・同じ権限で「Bash で python を実行せよ」と
  明示指示すれば fable-t-mid は正しく実行し出力を返す(6*7→42 で確認)。
- つまり **fcc/権限/ツールの問題ではなく、モデルが自発的にループを回さない行動の問題**。
  python モードでの fable-t-mid 9.5% vs raw-qwen 0% の差も、ループの効果ではない
  (どちらも回していない)。

## 07-20 続: 強制検証ループ(ハーネス側対策)の効果

プロンプト改善では行動が変わらなかったため、`run.ps1` に **loop アーム**
(`fable-t-mid-loop` / `fable-t-loop`)を追加。エージェント実行後にハーネスが
work 内の `test*.py` を実行し、無い/失敗していれば「課題文の入出力例をそのまま
アサートせよ、期待値やdocstringをコードに合わせて書き換えるな」と最大3ラウンド
再投入する(隠しテストは見せない)。モデルは3種のまま(既存 fable-t / fable-t-mid
の重みを再利用するアームであり、Ollama モデルは増やしていない)。

**csv-quotes(30B)での行動変化 — 誤魔化しが破れた:**

| | 通常アーム(誤魔化し) | loop アーム(強制) |
|---|---|---|
| 実装本体 | `split(",")` のまま、docstring だけ書換 | **引用符を見て分割する実装を実際に記述** |
| 自作テスト | 壊れた出力を正解としてアサート(緑で誤魔化す) | **課題の正しい期待値をアサート** |
| 隠しテスト | FAIL | FAIL(ただし要件1は充足) |

- 前進: 「壊れた実装＋それに合わせた偽テスト」という誤魔化しは破れ、
  要件1(引用符内カンマ)は正しく実装・正しく自己検証されるようになった。
- 残る欠陥: 30B は自作テストに要件2(`""`→`"` エスケープ)・要件3(未終端で
  ValueError)を含めず、不完全なまま緑にする。ハーネスは各要件を個別のテストとして
  要求するが、モデルの網羅性が足りない。
- 解釈: **検証ループの強制はプロンプトより有効**(fake→genuine の質的変化)。
  ただし30Bのテスト網羅性の限界までは埋められない。ここが 120B(fable-t-loop)で
  改善するかが次の焦点。
